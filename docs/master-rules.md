# Правила в кабинете мастера

Тексты хранятся в `src/data/masterRules.json` и включаются в страницы `/test/cabinet/master/` и `/test/cabinet/test-master/` при сборке Astro. Для хранения справочника не нужны таблицы или функции Supabase. Существующие Discord OAuth и таблица `user_profiles` используются для входа и проверки роли. Для новой роли `test_master` в работающей базе выполните `supabase/migrations/20261008_test_master_role.sql`; новая установка уже содержит её в `schema.sql`.

## Как открыть кабинет

В главном меню сайта выберите «Правила → Кабинет мастера». Прямой адрес — `/test/cabinet/master/`. Если вы ещё не вошли, сайт предложит авторизацию через Discord и вернёт в кабинет после входа. Доступ к интерфейсу есть у пользователей с ролью «Мастер» или «Администратор» в профиле сайта.

Пункт «Инструменты → Личный кабинет» открывает кабинет с учётом роли и выбранного ранее режима. Внутри кабинета режимы идут в порядке «Игрок / Тестовый мастер / Мастер / Администратор». Тестовик может пользоваться своим режимом и режимом игрока; мастер также может открыть режим тестовика; администратор может открыть все четыре режима.

«Правила → Кабинет тестового мастера» открывает `/test/cabinet/test-master/`. Роль `test_master` назначает администратор в таблице пользователей после запроса роли в Discord. Игроки не могут самостоятельно повысить себе роль. Роль мастера назначается после успешной тестовой игры; сайт не оценивает игру и не меняет роль автоматически.

В режиме тестовика доступны только готовые статьи с аудиторией `test_master`, чтение, поиск, избранное, скачивание и инструменты подготовки. Редактор, импорт, локальные правки и черновики мастера в этом режиме недоступны даже при просмотре администратором. Сейчас открыто только руководство `test-master-guide`; дополнительные статьи включаются явно в редакторе.

Создавать, редактировать и импортировать статьи в мастерском справочнике могут обе роли: «Мастер» и «Администратор». Правки сохраняются локально в браузере; общий сайт обновляется через экспорт файла и публикацию проекта. Управление пользователями и назначение ролей доступны только администратору.

## Локальная разработка без авторизации

Запустите `pnpm dev` (или `npm run dev`) и откройте `http://localhost:4321/test/cabinet/`. Если Astro выбрал другой порт, используйте адрес из вывода команды. При локальном обходе авторизации кабинет использует профиль с ролью `admin` и показывает переключатель «Игрок / Тестовый мастер / Мастер / Администратор». Discord не требуется, даже если переменные Supabase настроены.

При первом входе открывается административный режим. Следующий вход восстанавливает выбранный режим из отдельного dev-ключа `loh-test-account-dev-mode`. Сохранённый режим обычного аккаунта не влияет на локальный выбор. Прямые адреса `/test/cabinet/admin/`, `/test/cabinet/master/`, `/test/cabinet/test-master/` и `/test/cabinet/player/` открывают соответствующий режим независимо от сохранённого выбора.

В Windows PowerShell с запретом запуска `.ps1` используйте `pnpm.cmd dev` или `npm.cmd run dev`.

В этом режиме показано уведомление о локальной разработке. Правки, черновики и избранное хранятся отдельно под прежним ID `local-master-preview`, поэтому ранее сохранённые локальные правила остаются доступны. Для переноса правок скачайте файл правил. Клиент Supabase при обходе авторизации не создаётся, запросы к нему не отправляются.

В административном режиме таблица и статистика показывают локальный профиль; изменение облачных ролей и слотов недоступно. В режиме игрока можно открыть конструктор и проверить экспорт, а облачные персонажи и подключение расширения требуют настоящего аккаунта. В режиме мастера доступны статьи, поиск, избранное, редактор, импорт/экспорт и калькуляторы.

Режим разрешён только при `import.meta.env.DEV` на `localhost`, `127.0.0.1`, `[::1]` и в существующем dev-окружении `*.webcontainer.io`. В `pnpm build` / `pnpm preview` и на опубликованном сайте остаются обычные проверки Discord и роли.

## Где сохраняются изменения

Редактор сохраняет правки в `localStorage` этого браузера под ключом `loh-master-rule-changes:<ID аккаунта>`. Незавершённый текст и избранное имеют отдельные ключи с тем же ID. Они не передаются другим мастерам, не синхронизируются между устройствами и не изменяют опубликованный сайт. Очистка данных браузера удаляет эти копии; для переноса и резервного сохранения скачайте файл правил.

Статьи сайта доступны сразу после входа в кабинет. Локальные статьи и правки отмечены «Локально». Статус «Готово к публикации» в редакторе означает готовность текста, а не его публикацию для остальных пользователей.

## Добавление и редактирование

1. Откройте кабинет мастера и нажмите «Добавить правило» или «Редактировать» в статье.
2. Укажите раздел, заголовок, краткое описание, аудитории в поле «Кто видит правило» и текст Markdown. Выберите хотя бы одну роль. Предпросмотр показывает таблицы, списки и заголовки; HTML отображается как текст.
3. Нажмите «Сохранить в браузере». Для общего обновления используйте публикацию файла ниже.

«Вернуть версию сайта» убирает локальную правку выбранной статьи. Для новых локальных статей эта кнопка удаляет статью из браузера.

При изменении той же статьи в другой вкладке редактор проверяет номер редакции и текст исходной версии. Устаревшее изменение не перезаписывает актуальное. Когда новая версия сайта отличается от исходной версии локальной правки, показывается статья сайта, а локальная копия сохраняется отдельно. Её можно скачать или открыть в редакторе для сравнения и повторного сохранения. Копии статей, удалённых из файла сайта, также сохраняются в резервном экспорте.

## Публикация общих правил

1. Нажмите «Скачать правила» в кабинете. Получится `masterRules.json` с текущими статьями и совместимыми локальными правками. Если в открытом редакторе есть заполненный несохранённый текст, он также включается в файл.
2. Проверьте содержимое, включая статусы черновиков, и замените `src/data/masterRules.json` в проекте.
3. Соберите и опубликуйте сайт обычным способом. Новые тексты появятся у остальных мастеров в новой версии страницы.

При ручном редактировании JSON сохраняйте ID статьи. После изменения текста увеличивайте `revision` и обновляйте `updated_at`, чтобы различать редакции. Все тексты — строки; в `body` используется Markdown, таблицы записываются через `|`.

Поле `audiences` — непустой массив ролей, например `["test_master", "master"]`. Оно сохраняется при редактировании, импорте, экспорте и восстановлении черновиков. В старых файлах поле может отсутствовать: это означает `["master"]` и не открывает статью тестовикам автоматически. Администратор видит все статьи, тестовики — только `published`; мастер сохраняет доступ к черновикам своей аудитории. Аудитории задаются отдельно для каждой роли, поэтому статью можно показать только тестовикам. Изменение аудитории учитывается при обнаружении конфликтов локальных копий.

Чтобы в будущем добавить техническую роль, расширьте список ролей и доступных режимов в `src/utils/testAccount.ts`, список аудиторий в `src/utils/masterRules.ts` и ограничение профилей в миграции Supabase. Не требуется превращать техническую роль в ступень мастерской иерархии: доступ к статьям определяется явным списком аудиторий.

## Импорт и перенос

«Импортировать файл» читает JSON того же формата, проверяет структуру и сохраняет статьи локально. Совпадающие ID обновляются, отсутствующие в файле статьи остаются. Импорт не публикует изменения на сайте. Допускается файл до 10 МБ и до 2 000 статей. При наличии устаревших локальных правок кнопка «Скачать мои копии» создаёт отдельный резервный файл.

## Доступ к статическим текстам

Кабинет проверяет Discord и роль перед показом интерфейса. Тексты встроены в статическую страницу и доступны в её исходном коде без авторизации. Такой способ не обеспечивает конфиденциальность правил; закрытая выдача текстов потребовала бы серверной проверки доступа. Встроенный JSON экранируется, чтобы текст статьи не мог закрыть тег `script`.

## Содержание и инструменты

В файле 15 статей: 14 стартовых из `rule_dump.txt` и существующих правил сайта и руководство для тестовых мастеров. Фракции, разрешение конфликтов и денежная формула награды мастеру оставлены черновиками. Руководство содержит восемь критериев оценки и восемь шагов проведения тестовой игры. Ссылка на канал получения ролей и контакт для платного стола Roll20 в исходном тексте не заданы: пока канал назван текстом, а контакт предлагается уточнить у заверяющего. Калькуляторы используют исходные таблицы; редактирование текста не меняет их формулы автоматически. Генератор создаёт паспорт драконьего предмета, свойства которого нужно заполнить из его описания.

`supabase/migrations/20261003_master_rules.sql` теперь содержит только комментарии. Выполнять её не нужно. Если прежнюю версию уже применили, приложение больше не обращается к созданной таблице и функции; существующие записи остаются без изменений.

## Проверки

`npm run test:accounts` проверяет прямые адреса и переключатель всех четырёх режимов при dev-обходе, отдельный выбор режима, переход со страницы входа, отсутствие обращений к Supabase в dev и проверки сессии/ролей в production, включая запрет перехода тестовика в режимы мастера и администратора. Проверки выполняют настоящие клиентские скрипты с тестовыми границами DOM и Supabase; для них нужны установленные зависимости проекта.

`npm run test:master-rules` проверяет расчёты, безопасное отображение Markdown, стартовые статьи, импорт, локальные редакции и сохранность правок при обновлении сайта. Требуется Node.js 22.18+ или 24+, зависимости для этих тестов не нужны.

Файлы `src/utils/masterRules.test.ts` и `src/utils/masterRuleFiles.test.ts` содержат эти автоматические проверки. Они запускаются отдельно, не входят в интерфейс сайта и не обращаются к Supabase.

После установки зависимостей проекта выполните `npm run check:accounts` для проверки типов кабинета и справочника, `npm run check` для общей проверки проекта и `npm run build`. В браузере проверьте добавление, экспорт/импорт, восстановление незавершённого текста и одновременное редактирование в двух вкладках. Изменения справочника не должны отправлять запросы к таблицам Supabase.

При наличии локального Playwright из инструментов импорта книг можно выполнить `node scripts/check-master-preview.mjs` против dev-сервера. Скрипт проверяет чтение, поиск, избранное, редактор, отдельное хранилище правок, экспорт, калькуляторы, мобильный интерфейс и обычный вход при настроенном Supabase. Для проверки готовой сборки запустите `npm run preview` и повторите команду с `--production`. Адрес сервера задаётся переменной `MASTER_PREVIEW_URL`, по умолчанию используется `http://127.0.0.1:4321`. Проверка использует отдельные временные браузерные профили и не меняет исходный файл правил.
