# Дамп третьего сезона и развитие игровой статистики

Дата анализа: **2026-10-08**. Это исследование и предложение реализации. Страница, её источник данных и действующие правила не изменены; R03 не возобновлена.

## Вывод

Дамп позволяет расширить существующую статистику хронологией сообщений, названиями приключений, постоянными идентификаторами и проверяемыми начислениями. Но его числовые поля нельзя объявить проверенными: они повторяют ошибки сохранённого CSV. Первый этап — воспроизводимая проверка и исправления с источниками; второй — экспорт и изменение страницы. Историю персонажей следует добавлять отдельно после проверки связей.

## Что проверено

Источники: локальный `dnd.db`, сохранённый [CSV](research/master-rewards/stats.csv), [предыдущее исследование](master-rewards-evidence.md), [страница](../src/pages/tools/game-stats.astro), её [контроллер](../src/scripts/gameStatsPage.ts), [расчёты](../src/utils/gameStats.ts) и [фильтры](../src/utils/gameStatsView.ts).

Воспроизведение из корня проекта:

```powershell
python scripts/audit-game-stats.py
```

[Скрипт](../scripts/audit-game-stats.py) открывает SQLite в режиме `mode=ro`, включает `query_only` и сверяет SHA-256 базы до и после чтения. [Машиночитаемый отчёт](research/game-stats/audit.json) содержит структуру таблиц, счётчики, проверки связей и сравнение с CSV. Это исследовательский отчёт, не экспорт сайта. Проверка физической структуры `quick_check` вернула `ok`, `foreign_key_check` — без нарушений.

## Ошибки, требующие исправления до рейтинга по прогрессии

Это конкретные сопоставления поля и сохранённого текста. Они не являются полной оценкой частоты ошибок базы.

| Запись | Импортированное значение | Что сказано в тексте |
| --- | --- | --- |
| День 50, один игрок | 49 ОП | 49 пуль; общая награда — 6 ОП |
| День 118, один игрок | 30 ОП | Явно 5 ОП; 30 пм — выручка от продажи книг |
| День 254, один игрок | 347 ОП | Расход −347 пм; всем 2 ОП |
| Дни 312–313, один игрок | 60 ОП | 60 платиновых монет; всем 8 ОП |
| День 839, мастер | 32 МОП | Время 10:30–17:30, явно 7 МОП; далее в тексте участника встречается «32 мопса» |

Следствия:

- Число рядом с именем не является ОП без единицы и контекста. Ошибка затрагивает и игроков, и мастеров.
- Проверка только величин выше 12 недостаточна: неверное число может выглядеть обычным. В дампе 17 участий с ОП > 12 и одна запись мастера с МОП > 12 — это очередь проверки, а не правило отбраковки.
- В сообщении «День ~~52~~ 502» сохранён `day=52`. Нужен разбор исправлений и перечня дней; исправлять номер только по порядку строк нельзя.
- Сообщение о днях 312–313 содержит две сессии и два интервала времени, но `duration_hours=1`. Нельзя применять ко всем записям алгоритм одного интервала.
- Наличие ненулевого или заполненного поля не доказывает явное начисление в сообщении. Для нулей тоже нужна проверка: настоящий ноль и неудачный разбор различаются.

## Описание данных и предлагаемого экспорта

Названия ниже — предложение контракта, не существующий API.

| Исходные поля | Поля экспорта / трактовка |
| --- | --- |
| `games.message_id` | `recordId`: стабильная строка; связь с исходным сообщением хранится в служебном реестре |
| `channel_id`, `message_id` | Основа ссылки на сообщение; сервер Discord в `games` не записан, его нельзя угадывать из посторонней записи набора |
| `discord_date` | `messagePublishedAt`, ISO 8601 UTC; отдельно `playedAt: null`, пока дата игры не подтверждена |
| `day` и текст заголовка | `dayLabels`, `sourceDay`; массив допускает несколько сессий и исправленные номера |
| `title` | `title: string | null`; название не является ID приключения |
| `time_start`, `time_end`, `duration_hours` | Проверенные `intervals` и `elapsedMinutes`, либо `null`; исходные строки и округлённое значение остаются в исследовательских данных |
| `master_id`, `master_name` | `gmId`, отображаемое имя из словаря участников; алиасы отдельно |
| `master_mop` | `mopImported`, `mopAwarded: number | null`, качество и основание проверки |
| `participants.player_id`, `player_name` | Стабильный `playerId`, отображаемое имя; рейтинг строится по ID |
| `player_op`, `player_line` | `opImported`, `opAwarded: number | null`, источник значения и качество; потери прогрессии — отдельные события |
| `character_thread_id`, `character_match_status` | `characterCandidateId`, способ сопоставления; `characterId` только после достаточной проверки |
| `reward`, `status` | Необязательное описание; отсутствие значения явно обозначено. Статус импортера не выдаётся за состояние всей кампании |
| `characters` | Отдельный справочник анкет: имя, вид, класс, предыстория; текущее содержание не переносится автоматически на старые игры |
| `character_deaths` | Отдельные события со ссылками и причинами; в таблице нет надёжного FK к персонажу или игре |
| `character_forum_state`, `recruitment*`, `sqlite_sequence` | Служебные данные импортера/набора; для первой версии статистики не нужны |

Discord ID и любые другие большие идентификаторы хранить строками, не JS `number`. Для публичного набора достаточно стабильных внутренних ID и нужных отображаемых имён. Не экспортировать всю базу, полные анкеты, сырые сообщения и служебное состояние. Если публикуется ссылка на первоисточник, её доступность по-прежнему зависит от прав читателя в Discord.

Предлагаемый состав:

- `manifest.json`: версия схемы, ревизия набора, сезон, момент экспорта, время получения снимка если известно, диапазон **дат сообщений**, количество записей, краткие показатели покрытия, ссылки/хеши файлов.
- `games.json`: компактные записи, участники, проверенные начисления и метаданные качества. Достаточно для фильтров, таблиц и графиков первой версии.
- `people.json`: ID, выбранное отображаемое имя и необходимые алиасы. Явные переименования не создают новых людей.
- `details.json` либо файлы деталей по ID: необязательные описания наград и источники; загружаются при раскрытии записи.
- Служебные `audit.json`, `issues.json`, `overrides.json`: вне публичного каталога. Исправления адресуются ID сообщения и игрока, содержат старое/новое значение, основание и дату проверки.

`sourceSha256` идентифицирует снимок, но не заменяет дату его получения. `imported_at` отдельных строк не равен времени последнего изменения Discord. Времена экспорта и загрузки браузером показывать раздельно.

Качество вести **по полю**, например: `unreviewed`, `explicit`, `corrected`, `missing`, `conflict`. Простая структурная проверка не переводит все поля в `explicit`. Для совместных наград допустима ссылка на проверенную общую фразу, с приоритетом явных персональных исключений. Неизвестное значение — `null`, подтверждённый ноль — `0`.

## Как получить проверенный набор

1. Зафиксировать снимок, структуру и контрольные суммы. Выполнено для предоставленной базы; отчёт воспроизводится скриптом.
2. Сверять извлечённые начисления с `raw_text`/`player_line`: отдельная строка мастера, персональные награды, общая награда с исключениями. Деньги, уровни, количество предметов и потери не превращать в положительные ОП. Не восстанавливать ОП по часам или МОП мастера.
3. Сформировать очередь конфликтов: неизвестное начисление, разные явные значения, упоминание вне списка игроков, несколько сессий, исправленный номер, неоднозначное время. Сначала разобрать показанные ошибки и крайние значения, затем обычные записи; оставить нерешённые поля неизвестными.
4. Сохранять исправления отдельно от исходной базы. Повторный экспорт должен применять одни и те же решения и показывать, какие основания устарели после изменения исходного текста.
5. Проверить экспорт: уникальность стабильных ID, ссылки, обязательные поля, неотрицательные целые начисления, явные нули/пропуски, суммы по проверенным значениям и счётчики покрытия. Отрицательные события хранить отдельно; правило итогового зачёта не придумывать.
6. Сверить с CSV по содержимому и ID из базы, сохранив связь с прежними строками только как справочную. Не склеивать источники по номеру строки: порядок различается.
7. Проверить сценарии экспорта на реальных ошибках: «49 пуль», «−347 пм», «32 мопса», общие ОП с персональным исключением, нулевая/неизвестная награда, две сессии и исправленный день. Детерминированность проверять отдельно от времени создания манифеста.

Готовность первого набора не требует восстановления всей экономики. Требуется, чтобы каждое опубликованное начисление имело основание, нерешённые значения были обозначены и не попадали в сумму как нули, а перечень ограничений соответствовал выгрузке. Полноту списков игроков оценивать отдельно от полноты ОП.

## Как изменится текущая страница

Сейчас страница загружает CSV из GitHub при открытии и по кнопке, считает каждую строку одной партией, группирует по именам и присваивает ID по номеру строки. Уже есть фильтры мастера/игрока, личная карточка, столбцы/круговая диаграмма, рейтинги, таблица/мобильные карточки, пагинация и ссылка на выбранное представление. Их не следует объявлять новыми возможностями.

| Часть страницы | Изменение | Что получает пользователь |
| --- | --- | --- |
| Заголовок и источник | Название сезона, дата снимка если известна, границы дат сообщений, ревизия; получение браузером отдельно | Понятно, какой период и насколько свежие данные открыты |
| Фильтры | Добавить диапазон дат сообщений и поиск по названию; мастер/игрок выбираются по ID | Можно изучить месяц или найти нужный отчёт без разделения переименованного аккаунта |
| Сводка | «Записей об играх», уникальные игроки/мастера, средний состав; краткое покрытие проверенных начислений | Сообщение с двумя сессиями не обещает одну физическую игру; неполнота заметна |
| Графики | Сохранить распределения; добавить динамику записей и участий по месяцам публикации | Видны периоды активности. До подтверждения дат это не календарь фактически проведённых игр |
| Рейтинги | Отдельно ОП игроков и МОП мастеров; суммы только по проверенным значениям, рядом число записей с известным начислением | Ошибка с монетами не делает участника лидером, а неполная сумма не выглядит полной |
| Личная карточка | Существующие показатели дополнить датами первого/последнего отчёта в выборке и покрытием ОП | Можно оценить свою активность за выбранный период |
| Список партий | Дата сообщения, название, номер из текста, мастер, МОП, игроки/ОП; раскрытие деталей и первоисточника | Запись можно найти и проверить |
| Общая сумма | Основные итоги ОП и МОП раздельно; прежнюю сумму двух ролей, если сохранить, явно назвать комбинированной | Сумма перестаёт выглядеть прогрессией одного персонажа |
| Неизвестные поля | «Не указано» / «Не проверено», без подстановки нуля | Нет ложного вывода, что игрок ничего не получил |
| Ссылка на выборку | ID мастера/игрока, новые фильтры дат/названия в URL; чтение старых именных ссылок с проверкой неоднозначности | Сохраняется возможность поделиться фильтрами |
| Обновление | Повторная загрузка манифеста и файлов той же ревизии; сохранение прошлой успешной выборки при ошибке | Нельзя случайно смешать два снимка |

Фильтр игрока сейчас сохраняет весь состав подходящих партий и пересчитывает общие показатели по нему; личная карточка считает только выбранного игрока. Это поведение сохранить и объяснить. В динамике при фильтре игрока явно различать его личные участия и общую активность выбранных записей.

Для начислений с неполным покрытием предлагать формулировку «Подтверждено N ОП в X из Y записей», а не точную сумму всего заработанного. Средние по ОП делить на число известных начислений и показывать знаменатель. Остальная активность не исчезает из списка только из-за неизвестной награды. Для полностью неизвестной серии показывать отсутствие данных, а не нулевой результат.

Смерти, рейтинги по классам и персональная история персонажа — следующий этап. Нынешних привязок недостаточно для сравнения смертности классов; 247 событий не означают 247 окончательно погибших героев. Награды первой версии — описания в деталях, без рейтинга богатства, среднего золота за час и автоматической стоимости предметов.

## Источник обновлений и объём реализации

Рекомендуемая цель — компактный JSON с того же сайта вместо прямого CSV, с одним активным источником для всей выборки. Однако CSV сейчас обновляется независимо от сайта, а предоставленная база — фиксированный снимок. Подмена на локальный JSON без процесса обновления ухудшит свежесть.

Переход выполнять в два шага:

1. Подготовить и проверить архивный экспорт сезона, механизм исправлений и новый интерфейс на этом снимке. До замены источника явно обозначать снимок и его границы.
2. Подключить повторяемый путь «новый снимок базы → проверки → исправления → экспорт → публикация». Либо организовать обновление JSON рядом с текущим источником статистики. Только после этого обещать регулярно обновляемую статистику. Кнопка браузера не запускает импорт из Discord и не обновляет локальную базу.

Не объединять живой CSV и архив JSON автоматически: это одни и те же записи с разным составом полей, а после текущего снимка могут появиться новые игры. Любой явно выбранный режим должен иметь свои границы, источник и качество данных.

Основные места будущих правок:

- Новый валидатор/экспортёр и схема JSON; служебный реестр исправлений.
- `src/utils/gameStats.ts`: стабильные ID, раздельные ОП/МОП, неизвестные значения и покрытие; адаптер CSV при необходимости отдельного режима.
